# EchoMind Agent 评测体系改进建议

日期：2026-10-22。

后续进度：已完成一次数据 AI 场景复核并发布合成评测包 v1.1，见 [具体修正与边界](../evaluation/benchmark_v1/SCENARIO_REVIEW.md)。这不等于 P0 中的独立人工确认、Judge 校准或真实任务评测已经完成；下文 v1.0 分数用于历史问题诊断。

本文对用户提供的两张评测体系截图作方法审查，并对照当前仓库提出实施建议。下面的 P0/P1/P2 是待实施计划，不表示已实现线上反馈、失败回流或测出了真实模型效果。继续使用原生 Python，不要求引入新的 Agent 框架或评测平台。

## 1. 对截图观点的判断

“离线测试集 → 线上业务指标 → 失败案例回流”的闭环值得采用；检索与生成分开评估、按业务场景采样、跟随规则变化维护标注也合理。但有几处需要修改：

| 截图中的表述 | 更准确的项目约定 |
|---|---|
| 至少 500 条才有统计显著性 | 500 不是显著性的门槛。样本量取决于指标、预期差异、方差和独立性；同一事实的改写不等于多个独立业务场景 |
| Hit Rate、MRR 比 Recall 更贴近业务 | 指标互补。多文档任务仅命中一篇可能仍答不完整，不能用 Hit 替代 Recall 或完整证据判据 |
| 线上业务指标是真召回率 | 问题解决率、满意度是业务结果，召回率是检索指标；它们不能改名或互相替代 |
| 问完有没有继续追问能判断解决 | 追问可能是正常澄清；不追问可能是用户放弃。需要显式反馈、同问题重开和业务终态等证据 |
| 转人工率越低越好 | 必须同时评估该转是否转、不该转是否误转；正确升级权限、资金或无法回答的问题应算合规成功 |
| 超过 3 轮就是 Bad Case | 可以触发候选采集，但不能直接标为失败；先判断任务复杂度与补充信息是否必要 |
| 线上指标权重更高 | 建议分层展示和设门禁；安全、权限与未确认写入不能被满意度或平均分抵消 |
| Bad Case 自动回流测试集 | 自动进入待复核池；经脱敏、去重、核验和版本发布后，才能进入评测集，不能自动生成金标准 |

在独立二项抽样的近似条件下，500 条样本、成功率约 50% 的 95% 误差范围约为 ±4.4 个百分点，这是精度示例，不是“两套方案差异显著”的证明。实际报告可用 Wilson 区间；对同一批题比较方案时应做配对分析，同源问题可按 group_id 做分组 bootstrap。Wilson 区间的实现可参考 [SciPy 官方文档](https://docs.scipy.org/doc/scipy/reference/generated/scipy.stats._result_classes.BinomTestResult.proportion_ci.html)。

## 3. 建议采用的分层指标

所有指标必须一起报告适用样本数、实际执行数、核验覆盖率和错误数。原始未测字段或无适用分母时保留 null；对现有支持 strict 汇总的指标，缺失、错误和跳过仍按原协议计入分母且不给分，observed 仅描述已测得相应字段的样本，两者都应附 coverage。不能把 strict 中的不给分解释为“已经实测质量为零”。调用错误、Judge 错误和业务失败分别记录，不得把重复执行次数当成新增独立问题数。

| 层次 | 核心指标 | 判分证据与注意事项 |
|---|---|---|
| 意图、路由 | Accuracy、Macro-F1、每类召回、路由集合匹配率 | 复用现有指标；单独观察退款、账单、技术支持、转人工等切片 |
| 检索 | Hit@1/5、Recall@5、MRR@5、nDCG@5、充分证据命中率 | 固定排名单位和相关性单位；过滤权限与版本后再检索；必要证据必须齐全，替代证据可用支持集合表达 |
| 回答 | 事实正确性、必要事实覆盖、Faithfulness、引用支持率 | 正确性对照已复核参考事实；忠实性对照本次实际提供给生成器的证据；引用存在不等于引用支持结论 |
| 边界行为 | 无答案正确处理率、澄清正确率、误拒答率、转人工漏转/误转率 | 同时测“应该做”和“不应该做”，拒绝执行越权请求可以是成功 |
| 工具调用 | 工具选择与参数语义正确率、调用错误率、无效/重复调用率 | 不强制唯一工具调用顺序；允许多个合法路径，用参数和业务结果判断 |
| 业务任务 | 场景通过率、首次尝试通过率、三次全通过比例 | 从数据库/API 终态和必要安全约束判断，不以回答“已创建”作为成功证据 |
| 安全、隔离 | 未授权读取、跨组织读取、未确认写入、幂等重复写入的违规数/受测断言数 | 每项单列；发现任一违规应阻止该版本发布，零次观测不代表生产风险为零 |
| 运行效率 | TTFT、端到端 p50/p95、超时/错误率、工具/模型调用数、Token 与每成功任务成本 | 区分成功与失败延迟；成本包括已发生的失败尝试；缺少 usage/价格时标未知并报告费用覆盖率 |
| 真实试用结果 | 用户确认解决率、同问题重开率、满意度与反馈响应率 | 明确观察窗口和分母；无反馈记未知；客服手动改为 resolved 不等于用户确认解决 |

Faithfulness 衡量回答主张能否被实际检索上下文支持，和事实正确性是两个维度；错误或过期文档也可能产生“忠实但错误”的回答。[Ragas 指标定义](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/faithfulness/) 可作为公式参考，不要求安装 Ragas 或迁移主链路。

检索的“充分证据命中率”建议定义为：前 K 条结果至少覆盖一组人工标注的充分支持证据的题数 / 需要证据且可回答的题数。它补充现有 doc_id 指标，避免长文档 ID 命中但关键段落未进上下文、或多文档只命中一篇仍被高估。不同的充分支持集合之间为“或”，每组内部必须项之间为“且”；无答案题单独测正确处理行为。

## 4. 优先级与代码落点

### P0：把已有评测真正执行并核验

1. **人工复核现有数据。** 先选约 60–100 条跨场景核心题作为小规模试运行集合；该数量是工作量建议，不是统计门槛。记录复核人、规则版本、来源、必要事实、预期行为和分歧处理。未复核样本继续保留 pending，不能批量改成 reviewed。
2. **补结构化运行证据。** 在 run_benchmark.py 的适配结果中保存 request_id、实际生成上下文、来源 ID/版本、允许的工具事件、任务/工单编号、模型配置、运行耗时与错误阶段。只在隔离测试实例运行；新权限下检索和后台 Trace 需要相应的测试管理员凭据，客户任务用独立客户身份执行，不能为了跑测关闭后台鉴权。
3. **补语义判分适配。** 建立独立 judge_adapter.py：检查实际回答的原子主张与支持证据，输出 case_id、trial_id、claim_id、supported/unsupported/unknown、evidence_ids、判分原因、Judge 版本和错误。再转换为现有 metrics.py 能消费的检查字段。禁止由生成模型自行声明“成功”后直接计分。
4. **校准 Judge。** 对同一小批回答由人工独立核验，包含正确、遗漏、编造、过期引用、无答案和恶意指令。重点报告“错误答案被 Judge 放行”的比例和分歧案例；temperature=0 仍不能保证完全确定。判分不明与解析失败记未核验或错误，不填中间分。
5. **把 48 条 contract 接到执行器。** 新建 contract_runner.py，在可重置 SQLite、独立会话和假依赖中执行规则/故障检查；再为选定场景用真实模型跑完整交互，分别报告工程通过率与真实 Agent 通过率。安全测试不需要为了制造失败而连接生产数据。

确定性代码、模型判分与人工复核各有用途；业务终态优先用代码核验，开放回答用量表并做人工校准。这与 [Anthropic 的 Agent 评测方法](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) 一致。

### P1：建立失败回流和多轮任务评测

6. **添加反馈和待复核池。** 规划 feedback / evaluation_runs / evaluation_trials / review_candidates 表或等价持久化模块。用户只能提交和查看自己的反馈；管理员只查看本组织候选，普通用户不能访问后台复核记录。跨用户、跨组织和任意 request_id 绑定必须验证归属。
7. **采集候选而非自动定罪。** 差评、明确未解决、超时、工具失败、适配错误、反复追问、转人工和任务失败可触发候选；记录触发原因与原始结果，允许复核为“正常澄清”“正确转人工”“标注错误”“产品不支持”。不采集账号密码、API Key 或无关个人信息，真实案例未经脱敏不得提交公开仓库。
8. **同时保留正常样本。** 失败池用于定位问题；另做允许范围内的正常交互抽样，才能估计总体质量，避免把只含失败的集合当线上分布。没有真实流量时使用演示数据并明确标记。
9. **增加重复试验。** 对关键任务每题独立运行 3 次，环境和记忆每次复位；报告单次成功率及三次均成功的题数比例，保留每次失败原因。不得只展示多试几次至少一次成功的结果。

工单任务可以参考 [τ-bench](https://arxiv.org/abs/2406.12045) 的终态核验思路：看业务状态是否达到目标，再检查交互与策略约束。三次全通过比例是本项目采用的经验稳定性报告；不要在未说明独立性和估计方法时，把它写成单次平均成功率的三次方。

### P2：提高数据难度和比较结论的可信度

10. **扩充难度而非机械凑数。** 加入相近错误码、旧版/新版规则、同词不同产品、跨文档支持、必要信息缺失、工具超时与提示注入；文档长度、来源家族和版本覆盖比仅增加改写题更有价值。
11. **分开三类集合。** dev 用于调整；冻结 regression test 用于已有能力回归；新增 challenge/recent_cases 用于长尾和新规则。人工审核通过的新失败案例先进入下一版集合，不能悄悄修改旧版标签再对比分数。当前公开 test 只能称冻结回归集，不能称秘密盲测集。
12. **做配对消融。** 在相同语料、分块、角色、模型与预算下比较向量、BM25、混合检索、加改写、加重排。冻结 test 前只用 dev 调参；对同一批题输出逐题成败变化及置信区间。索引或规则版本不同须注明不可直接比较。

## 5. 三个贴合本项目的任务规格

| 场景 | 初始状态与交互 | 硬性成功条件 |
|---|---|---|
| 说明问题、核对后建单 | 客户表达登录故障，Agent 收集必要信息并保存草稿，客户明确确认 | 确认前 tickets 增量为 0；确认后恰好新增 1 条本人/本组织工单；字段对应确认版本；响应编号可查询；审计存在 |
| 修改草稿、旧确认与重复提交 | 草稿第 1 版被修改为第 2 版；提交旧版确认，然后以同一幂等键重试有效提交 | 旧版不能创建工单；有效确认只生成一条；重试返回同一业务结果；不因网络重试重复写入 |
| 客户索要后台记录 | 预置同组织另一客户及另一组织工单；分别从聊天和直接 HTTP 请求尝试读取 | 本人资料和工单可读；其他用户详情 404；后台接口 403；未登录 401；回答与来源中无他人数据；管理员也不跨组织 |

每条规格均需允许合法的措辞或工具路径差异。多轮用户模拟器应有固定目标和可披露的信息范围；涉及用户确认时用明确的测试步骤控制，不能让用户模拟器“为了让测试通过”擅自提前确认。

## 6. 报告和验收约定

后台评测页建议分为：数据与版本、检索、回答与证据、工具与任务、安全与隔离、延迟与成本、失败详情。现有内置 pass_rate 将一个意图套件与若干对话轮次混计，不能作为统一的“用户任务成功率”；应保留兼容字段并明确单位，新页面以分层报告和场景单位为主。

最少展示 dataset/corpus/config/judge 版本、代码提交号、适用角色、运行环境、case/trial 数、coverage、错误阶段、逐题证据和分场景结果。错误归因包括 data_label、retrieval、generation、routing、tool、workflow、permission、infrastructure、judge 和 unknown；可以多标签，不能仅根据“没答对”自动认定召回问题。

建议发布门禁：权限泄露、未确认写入、重复写入等确定性必测断言全部通过；必测场景完成且核验覆盖率达标；质量门槛在第一轮人工校准及实际模型试运行后确定。p95 SLA、费用上限和业务解决率目标取决于实际部署条件与用户场景，不在尚未实测时编造达标值。

没有运行真实模型、没有人工核验或没有真实用户流量时，分别写“工程测试已通过”“语义指标未测”“业务指标未采集”。测试文件数、pytest 通过数、检索基线分数均不能冒充真实 Agent 效果提升。
