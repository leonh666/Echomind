# 飞书工单接入指南

本功能将 EchoMind 中**用户核对并确认提交的工单**自动写入飞书多维表格，交给商家人工处理。客服主链路仍使用原生 Python，本次直接调用飞书官方 OpenAPI，没有引入 LangGraph、LangChain 或标准 MCP 客户端。

## 1. 接入后的流程和范围

```text
用户提出问题 → 创建待确认草稿 → 核对并确认提交
                                    ↓
                      本地工单和同步任务同时保存到 SQLite
                                    ↓
                      后台投递 → 飞书多维表格 → 人工跟进
```

- “建议人工核验”本身不代表已通知客服。需要在“工单处理”页确认提交工单，后台才会发送。
- 确认前会提示资料将同步飞书；只发送工单编号、标题、描述、分类、优先级、初始状态、创建时间和空备注。不会自动上传完整聊天记录、账号密码、邮箱、内部身份或任意 metadata。但用户主动写进描述的内容会被发送，应在提交前核对。
- 本版是**单向投递**。人工在飞书修改处理状态、备注，不会自动回写 EchoMind。项目内工单状态仍由项目里的客服或管理员维护；不要把“已交至飞书”当作“问题已解决”。
- 一套配置绑定一个组织和一张数据表。其他组织的工单不会发送到该表；管理员能查看全站用户目录，并不意味着跨组织工单会混合导出。
- 默认关闭；应用、表格和权限配置完整后再启用。既有工单不会批量补发，管理员可对尚未同步的活跃工单单独点“同步至飞书”。

## 2. 创建飞书多维表格

使用**飞书多维表格（Base）**，不是普通电子表格。建议新建一份专用的“EchoMind 人工客服工单”多维表格，创建数据表“待处理工单”。

为便于首次接入，以下列**全部设置为多行文本**，名称需要完全一致。默认的首列可以重命名为“工单编号”。字段可在飞书中调整顺序。

| 字段名 | 类型 | 内容 |
| --- | --- | --- |
| 工单编号 | 多行文本 | EchoMind 生成的唯一编号，用于防重复核对；请勿修改 |
| 问题标题 | 多行文本 | 简短的问题摘要 |
| 问题描述 | 多行文本 | 用户核对后的问题说明 |
| 问题分类 | 多行文本 | 一般问题 / 技术支持 / 账单问题 |
| 优先级 | 多行文本 | 低 / 普通 / 高 / 紧急 |
| 处理状态 | 多行文本 | 初始为“待受理”；可人工改为“处理中”等 |
| 创建时间 | 多行文本 | 带时区的 ISO 时间，默认 UTC，末尾 +00:00 |
| 处理备注 | 多行文本 | 初始为空，供人工填写结果 |

可以额外添加“负责人”“预计完成时间”等人工使用的字段，但不要添加 API 写入时必须填写的额外约束。第一版请保持上述字段为文本；单选、人员和日期字段的数据格式不同，配置检查会提示类型不符。

多维表格链接通常形如：

```text
https://你的组织.feishu.cn/base/这里是app_token?table=这里是table_id&view=...
```

- `app_token` 是 `/base/` 后的部分；它与飞书应用的 `App ID` 不同。
- `table_id` 是查询参数 `table=` 后的部分，通常以 `tbl` 开头。
- 如果分享链接是 `/wiki/` 链接，不要直接把 wiki 节点 token 当作 app_token。首次试点建议新建独立 Base，并按[飞书多维表格开发指南](https://open.feishu.cn/document/server-docs/docs/bitable-v1/overview)获取真正的 app_token。

## 3. 创建并授权飞书自建应用

1. 访问[飞书开放平台](https://open.feishu.cn/app)，在自己的企业/团队下创建企业自建应用，例如“EchoMind 客服工单”。需要具备创建或管理应用的权限。
2. 在应用的凭证页面取得 **App ID** 和 **App Secret**。App Secret 仅填写到后端本地 `.env`，不要放进前端、聊天、截图或 Git。
3. 在应用权限配置中开通多维表格的“获取字段”“查询记录”“新增记录”所需的**应用身份权限**。以对应官方 API 页面列出的权限为准；如果使用兼容的整组权限，其名称通常为“查看、评论、编辑和管理多维表格”（`bitable:app`）。发布/申请生效，让组织管理员按实际要求批准。
4. 在目标多维表格的应用/协作管理中，将该应用添加到**这份表格**并授予可编辑权限。不同版本入口可能位于“更多 → 添加文档应用”或应用管理菜单。只开通 API 权限并不等于获得已有表格的数据访问权限；如有高级权限，还要给应用对应的记录访问和编辑范围。
5. 本功能使用应用身份的 `tenant_access_token`，后台自动获取和刷新，不需要手动粘贴临时 token，也不需要配置聊天机器人或事件回调。

官方参考：[新增记录](https://open.feishu.cn/document/server-docs/docs/bitable-v1/app-table-record/create)、[飞书官方 Python SDK 中的新增记录参数](https://github.com/larksuite/oapi-sdk-python/blob/v2_main/lark_oapi/api/bitable/v1/model/create_app_table_record_request.py)。实际客户端使用项目已有的 httpx，只调用认证、字段读取、记录查询和记录新增接口。

## 4. 选择 EchoMind 组织并填写配置

在平时运行 `docker compose` 的 `EchoMindFrontend` 目录，列出本地业务组织：

```powershell
docker compose exec echomind python -m integrations.feishu --organizations
```

命令只读本地数据库，输出“组织编号 + 组织名称”，不输出密码或密钥。若非 Docker 运行，在后端 `EchoMind` 目录执行 `python -m integrations.feishu --organizations`。

选择实际接收工单的商家组织。公开注册默认进入“EchoMind 客户工作区”，它可能和管理员创建时的 Demo 组织不同：需要同步注册用户工单时，应绑定这些工单所属的组织。该配置不迁移账号、不改变注册归属，也不扩大原有工单权限。

试点时建议客服和用户处于同一个商家组织。新注册账号的归属可通过既有的 `ECHOMIND_REGISTRATION_ORGANIZATION_ID` 配置，历史账号不会自动迁移；已有账号/客服的组织成员设置见[管理员与用户权限说明](管理员与用户权限说明.md)。

编辑 **后端 `EchoMind/.env`**（不是前端 `.env`）：

```dotenv
ECHOMIND_FEISHU_ENABLED=true
ECHOMIND_FEISHU_ORGANIZATION_ID=填写上一步的组织编号
ECHOMIND_FEISHU_APP_ID=填写应用的AppID
ECHOMIND_FEISHU_APP_SECRET=填写应用的AppSecret
ECHOMIND_FEISHU_APP_TOKEN=填写Base的app_token
ECHOMIND_FEISHU_TABLE_ID=填写数据表的table_id
```

首次使用先从 `.env.example` 复制这六项，填好再将 enabled 改为 true。启用但配置不完整时会明确报错，避免让页面误以为已接通。密钥只保存在后端，接口不会返回它；`.env` 已在 Git 忽略规则中。

## 5. 更新服务和检查配置

在 `EchoMindFrontend` 目录执行：

```powershell
docker compose up -d --build
docker compose exec echomind python -m integrations.feishu --check
```

第一次更新需要构建新代码；更改 `.env` 后，需要重新创建/更新后端容器才能读取新环境。已有容器执行 `restart` 不会重新注入 env_file。无需修改 Compose 文件，后端已有 `env_file: ../EchoMind/.env`。

检查成功应显示：

```text
已连接飞书，工单字段检查通过；本次检查未写入记录
```

也可在工单页点击“检查飞书配置”，只有绑定组织内的管理员或客服可用。检查只获取应用凭证、读取字段，不创建测试工单。

## 6. 完成一条真实验证

1. 使用绑定组织中的账号登录 EchoMind。
2. 在“工单处理”中填写不含个人敏感信息的测试问题，例如“接入测试：退款进度需要人工核查”。保存草稿，此时飞书里不应出现记录。
3. 核对同步提示后点击“确认提交工单”。本地工单立即保存，并显示“等待同步至飞书”。
4. 通常几秒内后台完成写入；刷新工单页应显示“已交至飞书人工处理”。飞书中应新增一行，工单编号和本地一致。
5. 人工在飞书维护处理状态和备注，确认表格协作权限符合商家需要。EchoMind 本版不会读取这些人工字段或自动覆盖它们。
6. 连续刷新、重复确认已提交的草稿或对已成功同步的工单点重试，不应创建第二条记录。

同步任务不占用聊天模型调用。关闭页面后仍由后端继续处理；重启后会从 SQLite 恢复待发送任务。

## 7. 失败重试与排查

| 现象 | 处理方式 |
| --- | --- |
| 当前组织未启用 | 核对 enabled、组织编号和账号所在组织，重新创建后端容器 |
| 缺少/类型不符字段 | 按第 2 节创建同名的多行文本字段，再检查 |
| 无权限、找不到表 | 核对应用已发布、API 权限已生效、表格已授权该应用、app_token/table_id 正确 |
| 网络错误或限流 | 后台最多自动尝试 5 次，按退避间隔重试，工单仍保存在本地 |
| 同步失败 | 客服或管理员检查配置后，点该工单的“重试飞书同步” |
| 飞书同步已暂停 | 该工单绑定的组织/应用/表格与当前配置不同；恢复原目标配置或先人工核对，不会自动将旧任务改发到新表 |
| 重复工单编号 | 人工核对表格，不要修改“工单编号”；程序停止该工单的自动新增 |

本地工单、确认和 outbox 在一个数据库事务中提交。后台使用持久化租约限制并发投递；每次投递先查询飞书中的工单编号，再使用保存的同一个 UUID `client_token` 新增记录。这样可以处理写入成功但响应丢失、进程重启等常见情况。跨系统不存在本地事务级别的绝对“一次且仅一次”保证：飞书端的幂等有效范围以官方 API 为准，不要删除外部记录、改编号或让其他程序同时创建相同工单。

建议先用一张测试表完成上述验证，再填写真实商家资料。本地自动化验收使用独立 SQLite 和模拟飞书 HTTP 响应；在应用/表格未配置之前，不能宣称已完成真实飞书联调。
