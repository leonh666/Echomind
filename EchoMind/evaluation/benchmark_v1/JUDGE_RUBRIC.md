# 回答与业务结果复核规范

本规范用于给实际预测补充核验结果。原始题库全部为合成候选标签，人工复核仍为 pending；本文件不是“已完成人工评测”的证明。

## 1. 复核材料

复核人应同时看到：

1. 当前问题与实际对话历史。
2. 实际生成的 response，不能拿参考答案充当预测。
3. 实际检索并提供给模型的上下文与来源 ID。
4. 参考事实及来源文档；评正确性与完整性时使用。
5. 涉及业务任务时的数据库、接口、审计或事件证据。

只看到知识库全集，不能声称评了“回答相对于实际检索上下文的 Faithfulness”。当前 /chat 返回内容不足以完整评此项，需要补充请求级检索证据。

## 2. 行为标签

- answer：提供有依据的实质回答。
- clarify：关键产品、版本或必要条件缺失，先询问该条件。
- refuse：不确认无法获知或没有证据的具体结论。可以解释限制、给出安全下一步或建议授权查询，不要求拒绝整个服务。

例如“请告诉我现在实际退款是否到账”不能由静态政策推断。说明无法从资料确认实际到账，建议查询交易记录，属于本集的 refuse；编造“已经到账”不合格。

版本未知且资料存在互斥规则时，先询问版本为 clarify。直接比较多个版本并明确条件可能同样有帮助，首版采用严格主行为标签；出现合理替代答案时记录分歧，人工修订候选标签，不为追求高分临时宽松改判。

## 3. 参考事实覆盖

对每个 required_facts.id 标记：

- true：回答准确包含该事实，并保留关键版本、条件、否定或范围。
- false：遗漏、数值错误、条件错误，或与参考事实矛盾。
- null：尚未评判、材料不足或评判调用失败。

该指标衡量参考事实覆盖，不能发现所有额外编造。不要用简单关键词包含、数字包含或句子相似度直接代替语义核验。

## 4. Faithfulness

将实际回答拆成可核验的原子主张，逐条判断是否被“实际提供给模型的检索上下文”支持。特别记录回答新增的数值、政策、版本和执行承诺。

汇总到 faithfulness_checks：

- assessed：完成支持性核验的主张数量。
- supported：其中被实际上下文支持的主张数量。

没有上下文或未完成核验时省略此字段；没有可核验主张时可记 0/0，得分为 N/A。对模型本身的隐藏推理不做收集要求。

Faithfulness 高不等于来源正确，也不等于回答完整。一个完全照抄错误上下文的答案可能忠于上下文，却不符合参考事实。因此它与事实覆盖、引用和任务完成分开报告。

## 5. 引用

统计单位均为回答中的事实主张，不是链接数量：

- required：本次回答中需要证据支持的主张数，包含新增但无依据的主张。
- cited：其中具有存在、授权且版本匹配引用的主张数。
- assessed：已进一步核验引用是否支持主张的数量。
- supported：被所引用证据实际支持的数量。

约束：supported <= assessed <= cited <= required。无引用但需要证据时，例如 required=3、cited=0、assessed=0、supported=0，引用覆盖率为 0，支持率为 N/A。

不要把“只给正确的那一句加了引用”评为整体证据完整。

## 6. 工单和权限契约

每项 assertion 使用 true / false / null。true 必须附可追踪的业务证据；未实现、没运行或拿不到证据时使用 null，不根据“已创建工单”这句话赋 true。

建议保留 operation_id、ticket_id、数据库查询结果摘要、HTTP 状态或 trace 位置。只在独立测试环境执行故障注入。

## 7. 预测记录示例

以下是字段格式示意，ID 和计数应根据真实运行填写，不能作为本项目实测成绩：

```json
{
  "case_id": "rag-001",
  "status": "ok",
  "response": "待核验的实际回答",
  "behavior": "answer",
  "fact_checks": {"从本题复制的真实fact_id": true},
  "faithfulness_checks": {"assessed": 3, "supported": 2},
  "citation_checks": {"required": 3, "cited": 2, "assessed": 2, "supported": 1},
  "judge_method": "human",
  "reviewer_id": "reviewer-local-01",
  "reviewed_at": "实际复核时间",
  "claim_evidence": ["逐条主张与来源位置说明"]
}
```

正式数据中 fact_id 必须来自该题，脚本会拒绝未知 ID。示例没有列出 retrieved_document_ids；它应来自真实检索，不能直接复制题目的 relevant_document_ids。

## 8. 人工与 LLM Judge

首轮先检查所有来源规则与标签，抽取约 20～30 题双人复核评分标准；冻结测试集的答案与关键断言应逐题复核。记录一致率、分歧、修订理由和题库版本。

如用 LLM Judge，保存模型、Prompt、实际证据、逐项判定和错误状态。调用失败保留 null，不补 0.5。先用固定人工样本校准，再扩大规模。不要让同一个模型的生成与自评成为唯一证据。
